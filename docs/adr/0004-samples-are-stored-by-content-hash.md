# Samples are stored by content hash

A sampler's audio is referenced by the hash of its contents, not by a file path. The file itself is kept in a store beside the project, in the user library for saved groups and presets, and shipped as assets for system kits.

A preset, a saved group and a system drum kit all have to carry audio with them and keep working when moved to another machine. A path breaks as soon as the file moves; copying the file into each project makes the same kit a dozen unrelated files. A hash makes copies, presets and reloading identical, keeps one stored file however many samplers, presets and saved groups use it, and gives caches a key. We considered paths (simple, fragile) and per-project copies with relative paths (portable, duplicated), and chose the hash for portability without duplication. The cost is a store to manage and a rule for when unreferenced files are removed.

**Clips use the store too** (ADR 0012, chunk 8). An audio clip names its audio by hash (`AudioClip::hash`), and its `source` is only what the audio is called. The store sits beside the project file, in `samples/<hash>.wav`, the same folder the Sampler uses. Saving writes every hash a clip or a sampler names into it, so the project folder carries its audio. Until then a hash is played from wherever it was registered: a sound from a source plays from its cache object, and a file imported on the timeline from where it is, so dropping a sound needs no copy and no saved project. The registry is process-wide because a hash names its content, so any file with that content is as good as any other. Clips made by the app's own tools (recordings, stems, bounces, comped takes) still point at the files they wrote in the project folder by path; the engine plays both. A hash is of the decoded audio, so a file replaced on disk is a new sound, not a changed one.
