# Sample packs are published from main to R2

Noodle's sounds come from sources. A source is a static site of packs: a mutable `index.json` listing packs, one manifest per pack, and one immutable object per sample. The built-in source is a Cloudflare R2 bucket the project publishes to. Anyone can host another one anywhere that serves static files, and a user adds it with a URL and optional credentials, so libraries can be shared without us hosting them. A folder on the user's disk is a third kind of source and is read in place.

**Samples are addressed by content.** The object name is the hash of the decoded audio (`Sample::hash()`, ADR 0004). The audio travels as FLAC, which is lossless, so the hash of the decoded file is the hash of the sample. A changed sample is a new object and old objects are never deleted, so a project or preset that names a hash keeps working forever. A download is checked against its hash. The cache is keyed by hash, so the same sample from two sources is stored once.

**Only pack definitions live in git.** A pack is a RON file listing hashes, names, authors, licences and tags, and the pack definitions are reviewed in PRs like any other file. The audio is not in git, and it does not go through CI. Whoever makes a pack runs `noodle packs upload`, which adds the FLAC objects to R2, and then raises a PR with the definition. On merge to main, CI checks that every object the definition names is in R2 and decodes to the hash in its name, then writes the manifest and `index.json`. A definition whose audio was never uploaded fails the publish and changes nothing. Only the person making a pack uploads, for now Jeremy with his own R2 key. Letting contributors upload needs a credential of their own, and that is still open. R2 charges nothing for egress and the free tier covers reads at our scale, so a library of many gigabytes costs a few dollars a month.

**Licences travel with samples.** Each sample carries an author and a licence. The default for a pack someone creates lets everyone with access use the samples in their own projects, commercial or not, but not redistribute them. Authors can supply their own licence text for anything more restricted. A sample under CC-BY carries its credit with it, including when it is dropped on the timeline. The browser can filter by licence. We make no promise about the content of a source we do not run, and the add-source dialog says so.

**Crates.** `noodle-network` holds the network code: what is shared with the stem separator (ADR 0006: consent, a streamed download, a SHA-256 check and a content-keyed cache) and the S3 client publishing uses. `noodle-packs` reads and validates pack definitions and manifests, and does no I/O of its own beyond reading files. `noodle-publish` builds the static site and uploads it through `noodle-network`, for CI and for `noodle-cli packs build`. We avoid the word "library" for this, because it already means the user's saved nodes, groups and presets.

**Nothing in the audio path or the offline path touches the network.** `SampleStore` stays offline, and a sample not yet in the cache is fetched on a worker before it is used. The CLI and offline renders never download, so golden renders stay deterministic and a project that names a missing hash reports it instead of waiting.

**The Sounds panel and the create-source flow ship with this.** The panel is a general content browser, opened from the View menu, Cmd+K and the Sampler, that for now only has sounds. Nodes, groups and presets are the same kind of content and can join it as tabs later. Click auditions a sample, after a confirm above about 8 MB. Dragging onto a Sampler or a pad uses the hash. Dragging onto the timeline makes a clip that names the sample by hash and carries its credit, with no copy (ADR 0004). Sources are managed on a Sources page in settings, and the browser links to it. A folder is added as a source from the browser, where a right-click also offers "Make shareable pack…", a wizard that sets author, licence and tags, validates with the same code as CI and exports a static site or zip for the user to host. It never uploads.

We considered a per-user upload store (a moderation and abuse burden), a Git LFS or GitHub Releases host (bandwidth limits and no stable object names), serving from a Worker (CPU limits and request charges that static R2 reads avoid), and storing WAV (about twice the transfer for the same result).

The cost is a bucket and a publish credential to look after, a validator that has to stay in step with the app, and a rule for cleaning the cache. Hosts we do not control can serve anything, so the hash check, the licence field and the warning are the only protection.
